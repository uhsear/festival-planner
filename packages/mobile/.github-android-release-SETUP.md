# Android release on GitHub Actions — one-time setup

This replaces `eas build -p android` / `eas submit -p android` with a free,
GitHub-hosted build defined in [`.github/workflows/android-release.yml`](../../.github/workflows/android-release.yml).

The workflow regenerates `android/` with `expo prebuild`, signs the release AAB
with our **Play upload key** (injected by the
[`withAndroidUploadSigning`](./plugins/withAndroidUploadSigning.js) config plugin),
uploads the AAB as an artifact, and — when you pass `submit=true` — pushes it to
Google Play as a **draft**.

> **Play App Signing is enabled.** The AAB is signed with the *upload* key only;
> Google re-signs it with the real app-signing key on their side. The upload key
> **never rotates**, so these secrets are long-lived — set them once.

You only need to do this **once**. After that, releases are a single
`gh workflow run`.

---

## 1. Export the upload keystore from EAS

EAS currently holds the upload key. Download it locally:

```sh
cd packages/mobile
eas credentials -p android
# → select the production build profile
# → Keystore: Manage everything needed to build your project
# → Download existing keystore
```

This gives you a `.jks`/`.keystore` file plus the **keystore password**, **key
alias**, and **key password** (EAS prints them, or they're in the downloaded
`credentials.json`). Keep these — they go into GitHub secrets below.

## 2. Verify the keystore matches Play Console's upload certificate

Before trusting it, confirm the keystore's SHA-1 matches the **upload
certificate** registered in Play Console (Play Console → your app → **Setup →
App integrity → App signing → Upload key certificate**):

```sh
keytool -list -v -keystore /path/to/uploaded.keystore -alias <YOUR_KEY_ALIAS>
# Compare the printed SHA-1 / SHA-256 to the Upload certificate fingerprints in
# Play Console. They MUST match — otherwise Google will reject the upload with
# "Your APK signing certificate is not the one expected".
```

If they don't match, you have the wrong keystore (or wrong alias) — do not
proceed.

## 3. Base64-encode the keystore

GitHub secrets are text, so the binary keystore must be base64-encoded.

```sh
# macOS / Linux:
base64 -i /path/to/uploaded.keystore | tr -d '\n' > keystore.b64

# Windows PowerShell:
[Convert]::ToBase64String([IO.File]::ReadAllBytes("C:\path\to\uploaded.keystore")) | Out-File -Encoding ascii keystore.b64
```

## 4. Set the GitHub secrets

Using the `gh` CLI from the repo root (or add them in the repo's
**Settings → Secrets and variables → Actions**):

```sh
# --- signing (required) ---
gh secret set ANDROID_KEYSTORE_BASE64   < keystore.b64
gh secret set ANDROID_KEY_ALIAS         --body "<your key alias>"
gh secret set ANDROID_KEYSTORE_PASSWORD --body "<your keystore (store) password>"
gh secret set ANDROID_KEY_PASSWORD      --body "<your key password>"

# --- Play submission (required only if you ever run with submit=true) ---
gh secret set PLAY_SERVICE_ACCOUNT_JSON < "C:/Users/lolzi/Downloads/festie-498100-XXXX.json"

# --- Sentry source maps / symbols (optional) ---
gh secret set SENTRY_AUTH_TOKEN --body "<sentry auth token with project:releases scope>"
```

> Delete `keystore.b64` afterward — it is the upload key in plaintext-ish form.

### Required secrets summary

| Secret | Required | Purpose |
|--------|----------|---------|
| `ANDROID_KEYSTORE_BASE64` | yes | base64 of the upload `.keystore` |
| `ANDROID_KEY_ALIAS` | yes | key alias inside the keystore |
| `ANDROID_KEYSTORE_PASSWORD` | yes | keystore (store) password |
| `ANDROID_KEY_PASSWORD` | yes | key password |
| `PLAY_SERVICE_ACCOUNT_JSON` | only if `submit=true` | Google Play service-account JSON (Play Console → Setup → API access; grant the SA "Release to testing/production" / app-level release permissions) |
| `SENTRY_AUTH_TOKEN` | optional | uploads JS source maps + native symbols so prod crashes symbolicate. If unset, the build sets `SENTRY_DISABLE_AUTO_UPLOAD=true` and skips upload (AAB still builds). |

## 5. Set the versionCode offset

Android requires every uploaded AAB to have a **strictly increasing** integer
`versionCode`. EAS was auto-incrementing it remotely, so the last EAS-published
build has some code `N`. The workflow computes:

```
versionCode = VERSION_CODE_OFFSET + github.run_number
```

1. Find the **last published versionCode** in Play Console:
   **Release → (Internal/Production) → App bundle explorer** (or any release's
   bundle details).
2. Open [`.github/workflows/android-release.yml`](../../.github/workflows/android-release.yml)
   and set `VERSION_CODE_OFFSET` (in the `env:` block) so the **first** GH build
   already exceeds `N`. Simplest safe rule: **`VERSION_CODE_OFFSET = N + 100`**.
   - e.g. last EAS code `42` → set `VERSION_CODE_OFFSET: '142'`.
   - The `+100` headroom absorbs the current `run_number` and any past
     workflow_dispatch runs so you never collide.

> **Collision risk:** if the offset is too low, Play rejects the upload with
> *"Version code N has already been used."* Bumping the offset and re-running
> fixes it. versionCode only ever needs to go up, never down.

## 6. First run — build only (no submit)

Verify the AAB builds and is correctly signed **before** touching Play:

```sh
gh workflow run android-release.yml --ref <your-branch> -f submit=false
gh run watch   # or watch in the Actions tab
```

When it's green, download the `festie-release-aab-<versionCode>` artifact and
sanity-check the signer:

```sh
# Optional local verification:
jarsigner -verify -verbose -certs app-release.aab
# or, with bundletool, build APKs and check the signing cert matches Play's upload cert.
```

## 7. Submit to Play (draft)

Once you trust the build, submit:

```sh
gh workflow run android-release.yml --ref <your-branch> -f submit=true -f track=internal
```

This uploads to the **internal** track as a **draft** (same as the old
`eas submit`). Promote/roll out from Play Console as usual. Use
`-f track=production` (still draft) when you're ready for a production release.

## Notes & gotchas

- **Build time:** the all-ABI New-Arch release build is ~35-55 min on a free
  runner (vs single-ABI for the E2E smoke). `timeout-minutes: 90` gives headroom.
- **No EAS coupling:** this path doesn't touch EAS Update channels. If you also
  ship OTA updates via `eas update`, keep `runtimeVersion.policy: fingerprint`
  in mind — a native change here produces a new fingerprint, so OTA updates must
  target the matching runtime. (Unchanged from before; just noting it.)
- **Local/EAS builds are unaffected:** the signing plugin only activates when the
  `MYAPP_UPLOAD_STORE_FILE` gradle property is present, which only the CI step
  sets. Local `expo run:android` and any EAS builds fall back to the debug
  signingConfig exactly as before.
- **Service-account permissions:** if submit fails with a 403, the Play
  service account lacks release permission for the app — grant it in Play Console
  → **Users and permissions** (app-level) or **Setup → API access**.
